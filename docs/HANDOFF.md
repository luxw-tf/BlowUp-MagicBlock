## Product scope and owner decisions

The [PRD](../BlowUp-PRD-v0.1.docx) sets a six-seat target with bot fill, instant tags, dodgeable throws, a randomized fuse after each transfer, five eliminations, spectating and rematch. Four pickups on the dock grant one of six abilities. It asks for 60 FPS, 20 Hz simulation, under 100 ms p95 input confirmation, under 10 s matchmaking, under 20 s guest-to-game and a 2–4 minute match. Those are targets. The original fuse table, orthographic camera and character sketches predate the current tuning, perspective camera and KayKit cast.

At the final design checkpoint, the owner selected **on-chain per-wallet progress**, **one free message signature to link** and **no wallet prompts during gameplay**. Track matches, wins, podiums, passes and bombs received. Branding belongs on **loading and title screens** and **lobby screens**. Personal bests, a recent match list, a menu branding badge and branding in the match/results UI were offered but were outside the selected scope. Guests must still be able to play without funding or connecting a wallet. Wallet-linked players still play and reconnect with the guest identity and session key.

Claude identified the [Solana brand resources](https://solana.com/branding) and a [MagicBlock press kit](https://drive.google.com/drive/folders/1-BdkdHYddZ5Xt113vtLcVu1UixXrRSP7) via MagicBlock's official site. The session stopped before choosing or adding assets. Confirm usage against the official resources when implementing.

## Current architecture

| Area | Entry points and responsibility |
| --- | --- |
| Browser | React 18, TypeScript, Vite, Three.js and React Three Fiber. `src/App.tsx` routes the landing menu, tutorial, offline lobby, online queue, private room and match. `src/ui/Menus.tsx` owns the loading veil, title and mode picker. `src/render/MenuStage.tsx` stages the live harbour and title crew. |
| Offline | `src/game/sim.ts` is a renderer-independent fixed 20 Hz state machine. `session.ts` dispatches explicit random requests using `LocalDevRandomness`, retries, and exposes `SessionLike`. `bots.ts` produces ordinary input frames. `arena.ts`, `config.ts` and `content.ts` hold layouts, tuning and game content. |
| Browser online | `src/ui/onlineFlow.ts` builds join payloads, polls setup and rejoins. `src/chain/online-session.ts` persists a browser guest identity, makes ephemeral session signers, predicts local movement, sends absolute position inputs, animates local throws and mirrors chain outcomes. `mirror.ts` decodes snapshots into game state and derived events. `VerificationPanel.tsx` shows online VRF and settlement evidence. |
| Shared client | `src/chain/program.ts` owns PDAs, IDL-backed instruction builders, account decoders, blockhash/send helpers, subscriptions with a polling fallback, and an extrapolated ER slot clock. Client IDL is `src/chain/blowup.idl.json`. |
| Lobby | `server/index.ts` is a Node HTTP server. `lobby.ts` holds in-memory tickets, queue and private rooms. `match-runner.ts` sponsors setup, chooses the nearest ER route, delegates the match and player accounts, runs bots/takeovers and the elimination crank, retries VRF, finalizes and records results. Gameplay uses the players' session keys directly on the ER. |
| Program and tooling | `programs/blowup/src/lib.rs` contains the Anchor instructions and constraints, `state.rs` the accounts, `rules.rs` the mechanics, and `errors.rs` the errors. Rust uses Anchor 1.0.2 and MagicBlock SDK 0.18.0. TypeScript uses Anchor 0.32.1, web3.js 1.x and the pinned MagicBlock TS SDK 0.18.0. `chain/` has its own manifest and committed IDL. The IDL copies are byte-identical. |

The lobby batches base-layer create/join, delegates all occupied accounts, waits for routing, then starts on the ER. The ER validates input sequence, signer, expiry and movement bounds. Transfers validate holder, target, range, phase and fuse/protection timing. The VRF callback verifies the oracle identity and outstanding nonce. Holder and fuse draws use purpose-tagged SHA-256 over the VRF output. Deadlines use ER slots and route `blockTimeMs`. The lobby normally cranks eliminations as deadlines pass, finalizes via commit-and-undelegate, waits for base ownership and creates the durable `MatchResult` PDA. Account subscriptions have a polling fallback. Browsers and bots stream inputs at about 10 Hz, even though prediction is stepped at 20 Hz.

Quick play waits eight seconds or starts when six humans are queued. Private rooms use a five-character code or `?room=CODE`, readiness and host-controlled bot fill. Teams can run rooms of 2–6 humans without bots. The lobby applies 15 s grace before the first input and 6 s silence after activity. The program has a 5 s takeover guard for a seat that has sent inputs. A bot temporarily uses the seat's session key slot. The original identity can renew the session to reclaim it, including after reload. The lobby is process-local and its state disappears on restart.

Confirmation-level issues, delayed RPC reads and a byte-identical idempotency retry were harness problems and were corrected. ## Wallet progress implementation audit

- `MatchState` appends `wallets[6]`, `passes[6]` and `received[6]`. The default public key is the guest sentinel. `join_match` accepts a new required wallet argument on the wire and trusts the authority of that match to supply it. A successful pass increases the sender's passes and the target's received count. A round-opening holder draw also counts as received.
- `PlayerProfile` PDA seeds are `["profile", wallet]`. It stores the wallet, lifetime matches, wins, podiums, passes, received, last match, updated slot and bump. Placement zero is excluded from win/podium accounting. `record_progress(seat)` is permissionless with a payer, operates on a finished match and its settled result, verifies the seat's linked wallet, creates a profile as needed and updates it. The appended `MatchResult.progress_recorded` bitmask enforces one credit per seat per match. It does not impose one credit per distinct wallet per match if the wallet occupies multiple seats. Consider that deliberately during lobby integration. A single pointer to the last recorded match is already implemented. The account does not store a list of matches.
- `src/chain/program.ts` adds `pda.profile`, `decodeProfile`, the new match/result fields and `recordProgress`. Its optional TypeScript wallet parameter supplies the default sentinel for existing callers. `chain/feasibility.ts` builds its own raw Anchor `joinMatch` call and still sends four arguments. Its dynamic typing lets the chain typecheck pass despite the incompatible instruction call. Update that call before using the harness.
- `src/chain/wallet-link.ts` defines an exact UTF-8 message binding wallet, guest identity and ISO issuance time, with a base64 signature in the payload. `server/wallet-verify.ts` verifies Ed25519 with Node crypto and enforces exact text, identity, wallet, a 24-hour age limit and five minutes of future skew. The five passing tests exercise this helper. Proof is time-bounded and reusable with the same identity while valid. It proves wallet ownership at the lobby boundary. The program itself does not verify the off-chain signature.
- `server/index.ts` still parses only name, character, identity, session and session expiry for all three join endpoints. `HumanJoin` has no wallet field. `MatchRunner` calls the join builder without a wallet and only sends `record_result` at settlement. The browser's `joinPayload` has no proof. `OnlineLobby` and `RoomScreen` already use that common helper. There are no brand assets or wallet UI changes in the latest commit.
- ABI break: appending fields preserved existing offsets but increased account lengths. Current decoders expect the new layout and can fail on older settled match/result accounts. Older lobby/harness code sends the old join shape and is incompatible with the recorded upgraded program. Keep the program, both IDLs and all callers in sync. Current local guest compatibility follows from the builder default and still needs a live post-upgrade smoke test. Historical report decoding may need version-aware tooling.
